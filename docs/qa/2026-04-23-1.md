## ✍️ Minhas Respostas

### 1.
O fluxo correto do TDD (Test-Driven Development) segue o ciclo Red -> Green -> Refactor. Primeiro, escrevemos um teste e verificamos que ele falha. Em seguida, implementamos no módulo testado as condições necessárias para que o teste passe. Depois disso, refatoramos o código sem alterar o comportamento validado. Esse ciclo se repete a cada novo comportamento esperado, até que os principais casos de falha estejam cobertos.

Quando um teste não é satisfeito pelo módulo em desenvolvimento, isso pode indicar um dos seguintes problemas:

1. O teste realmente cobre o comportamento que queremos desenvolver ou evitar?
2. O teste está complexo demais, contendo mais de um caso por vez? É possível dividi-lo em testes menores para validar cada caso separadamente?

O primeiro problema é resolvido validando o objetivo do módulo. Quando há muitos objetivos sobrepostos, o desenvolvimento perde foco. Por isso, cada módulo deve ter uma responsabilidade específica dentro do projeto.

O segundo problema é resolvido avaliando cada test case separadamente. Cada teste deve validar apenas um caso por vez. Em `test_interfaces.py`, por exemplo, o test case `test_incomplete_loader_does_not_satisfy_protocol` verifica exclusivamente se um loader incompleto satisfaz ou não o protocolo de `BaseLoader`. Essa separação facilita a manutenção e delimita melhor o comportamento esperado.

Se a ordem for invertida, começando pela implementação antes dos testes, aumentamos o risco de criar erros ocultos, comportamentos inesperados e validações incompletas. Os testes funcionam como balizadores do que o módulo deve oferecer, como verificar se uma condição existe, se um valor é negativo, nulo ou inválido.

### 2.
Os protocolos presentes em `interfaces.py` precisam de `@runtime_checkable` que permite o uso de `isinstance()`, para que os testes com eles sejam relaizados sem problemas em tempo de execução com o `test_interfaces.py`
Caso esse decorator seja removido, os asserts com esse tipo de estrutura não poderão funcionar.


### 3.
`chunk_id` e `chunk_index` são parâmetros diferentes um do outro, enquanto o `chunk_index` é um positional index, indicando a posição do chunk dentro da fonte original, o `chunk_id` se explica como um identificador para o `DocumentChunk` como uma entidade que pode ser manipulável pelo sistema, como com vetores, grafos, retrievers ou logs e pode carregar informações de rastreabilidade.
`chunk_index` indica posição, e `chunk_id` descreve a identidade.

Definindo de forma prática:

`chunk_index` = 0
`chunk_id` = bearing-failure-analysis-2013-12-p12-c0

Repare que `chunk_id`, contém de maneira explícita, além do nome do arquivo "bearing-failure-analysis-2013-12", a página "p12", que é um parâmetro de `SourceRef` e o próprio `chunk_index`, referenciado como "c0".

### 4.
O `TypedDict` é um recurso de tipagem, que descreve qual deve ser o formato esperado de um `dict`.
Por exemplo:

O `SourceRef` é um `TypedDict` com esse formato:

```python
class SourceRef(TypedDict):
    filename: str
    page: int | None
    chunk_index: int | None
```
Portanto ele é um dicionário que deve ter as chaves `filename`, `page`, `chunk_index`, sendo que as duas últimas além de serem do tipo `int`, também podem ser `None`, sendo em runtime ele pode ter um formato desse:

```python
source_ref ={
    "filename": "bearing-catalog.pdf",
    "page": 45,
    "chunk_index": 350,
}
```

O `TypedDict` auxilia _static type checkers_ como o `mypy` e `pyright`, a entender quais campos existem, e com que tipo eles precisam ser preenchidos, porém não possui validação automática em tempo de execução.

Já o Pydantic é uma biblioteca para criação de modelos de dados com **validação em tempo de execução**, sendo que esse objeto pode ter uma exception lançada caso algo esteja inválido durante a execução.

`DocumentChunk`, `SourceRef` e `ExtractionResult` além dos outros, descrevem o formato que é esperado de dicionários, considerando suas chaves e a tipagem dos seus valores, podendo ser capturados por _static type checkers_, sendo contratos firmados entre camadas do próprio sistema, ou seja a camada mais externa que recebe os dados externos (PDFs, CSV, etc) é que poderá possuir o Pydantic ou outra forma de runtime validation, pois a estrutura desses dados é extremamente variável, sendo responsável pelo ETL dos mesmos.
O `TypedDict` documenta e tipa corretamente o formato esperado internamente que foi tratado por camadas mais externas (boundary validation).


### 5.

As classes que estão presentes em `__init__.py` são somente os Protocols pois eles são os contratos de comportamento que as demais implementações devem seguir, por isso são listados na API pública de `nexusrcm`, sendo importados como `from nexusrcm import ...`, ao contrário dos `TypedDicts` que se forem acessadas vão precisar de `from nexusrcm.interfaces import ...`

## Vocabulário Técnico

- **TDD / Test-Driven Development (desenvolvimento orientado por testes)**: prática de desenvolvimento em que os testes são escritos antes da implementação. O objetivo é transformar o comportamento esperado em uma especificação verificável antes de escrever o production code.
- **Red -> Green -> Refactor**: ciclo central do TDD. **Red** confirma que o teste falha pelo motivo esperado; **Green** implementa o mínimo necessário para o teste passar; **Refactor** melhora o código preservando o comportamento validado pelos testes.
- **Executable Specification (especificação executável)**: forma de descrever o comportamento esperado por meio de automated tests. Em vez de depender apenas de documentação textual, o projeto passa a ter regras que podem ser executadas e verificadas.
- **Interface Contract (contrato de interface)**: definição explícita do que uma implementação precisa oferecer para ser considerada compatível com uma camada do sistema. No projeto, `BaseLoader` define que qualquer concrete loader precisa expor `load(source: Path) -> list[DocumentChunk]`.
- **Protocol**: recurso de structural typing do Python usado para definir contratos sem exigir direct inheritance. Uma classe satisfaz um `Protocol` se tiver os métodos e atributos esperados, mesmo sem herdar dele.
- **Structural Typing (tipagem estrutural)**: modelo em que a compatibilidade é determinada pela forma do objeto, isto é, pelos métodos e atributos disponíveis. Isso difere de **Nominal Typing**, em que a compatibilidade depende do nome da classe ou de herança explícita.
- **Nominal Typing (tipagem nominal)**: modelo em que a compatibilidade depende de herança, registro explícito ou identidade nominal da classe. É o contraste direto com structural typing.
- **Direct Coupling (acoplamento direto)**: dependência forte entre uma parte do sistema e uma concrete implementation. Quanto maior o direct coupling, mais difícil fica trocar, testar ou evoluir componentes isoladamente.
- **Decoupling (desacoplamento)**: redução da dependência entre módulos concretos. Usar contratos como `BaseLoader`, `BaseExtractor` e `GraphStore` permite que outras partes do sistema dependam da interface esperada, não da implementação específica.
- **Concrete Implementation (implementação concreta)**: classe ou função real que executa o comportamento definido por um contrato. Por exemplo, futuramente um `PdfLoader` ou `CsvLoader` pode ser uma concrete implementation do contrato `BaseLoader`.
- **Contract Test (teste de contrato)**: teste que verifica se uma implementação respeita a interface esperada. Em `test_interfaces.py`, os testes confirmam que classes dummy satisfazem os Protocols definidos para loader, extractor, stores, retriever e agent.
- **Structural Test (teste estrutural)**: teste que valida a presença da estrutura esperada, como métodos e assinaturas, sem necessariamente validar todo o comportamento interno. Os primeiros commits validam mais a estrutura dos contratos do que a lógica completa de ingestion.
- **Behavioral Test (teste comportamental)**: teste que valida o resultado produzido por uma ação do sistema. No futuro, concrete loaders precisarão de behavioral tests para verificar se PDF, CSV ou JSON são realmente convertidos em `DocumentChunk` corretamente.
- **Confirmation Bias (viés de confirmação)**: risco de escrever testes depois da implementação e acabar validando apenas o código que já existe, em vez de questionar se ele representa o comportamento correto. No TDD, escrever o teste antes reduz esse risco.
- **Public API (API pública)**: conjunto de símbolos que o pacote expõe como forma recomendada de uso. O `src/nexusrcm/__init__.py` re-exporta os Protocols principais para sinalizar quais abstrações são centrais e estáveis.
- **Re-export**: prática de importar um símbolo em um módulo e exportá-lo novamente por outro ponto de entrada. Neste projeto, `nexusrcm.__init__` re-exporta `BaseLoader`, `GraphStore` e outros Protocols para facilitar imports como `from nexusrcm import BaseLoader`.
- **Abstraction Layer (camada de abstração)**: ponto intermediário que esconde detalhes de implementação e expõe apenas o contrato necessário para outras partes do sistema. Os Protocols funcionam como uma abstraction layer entre a arquitetura e os componentes concretos.
- **Production Code (código de produção)**: código principal da aplicação, em contraste com test code. No fluxo TDD destes commits, `src/nexusrcm/interfaces.py` é production code e `tests/test_interfaces.py` é test code.
- **Test Code (código de teste)**: código usado para validar o comportamento ou a estrutura do production code. O commit `test(ingestion): add protocol contract coverage` adiciona test code antes da implementação dos contratos.
- **Chunking (segmentação em trechos)**: processo de dividir um documento grande em unidades menores de texto. No projeto, cada unidade gerada pelo processo de chunking é representada por um `DocumentChunk`.
- **Chunk (trecho)**: unidade normalizada de texto produzida pela ingestion layer. Um chunk deve carregar tanto o conteúdo textual quanto informações de origem para permitir retrieval, auditabilidade e rastreabilidade.
- **Identifier / ID (identificador)**: valor usado para identificar uma entidade de forma estável dentro do sistema. `chunk_id` é um identifier do `DocumentChunk`, útil para referência interna no pipeline.
- **Positional Index (índice posicional)**: número que representa a posição de um item dentro de uma sequência. `chunk_index` é um positional index porque indica a ordem do chunk dentro da fonte original.
- **Source Reference (referência da fonte)**: estrutura que aponta para a origem de uma informação. No projeto, `SourceRef` guarda `filename`, `page` e `chunk_index` para conectar um chunk ao documento original.
- **Provenance (proveniência/origem)**: capacidade de explicar de onde uma informação veio. `source_ref` preserva provenance ao indicar arquivo, página e posição do trecho usado como evidência.
- **Traceability (rastreabilidade)**: capacidade de seguir uma informação desde a resposta final até a fonte original. A combinação de `source_ref`, `chunk_index` e `chunk_id` ajuda a manter traceability no pipeline.
- **TypedDict**: recurso de typing do Python usado para descrever o shape esperado de um `dict`. Ele ajuda static type checkers a entenderem quais keys existem e quais tipos seus values devem ter, mas não valida dados automaticamente em runtime.
- **Pydantic**: biblioteca para criar data models com runtime validation. É útil para validar e normalizar dados vindos de fora do sistema, como API payloads, JSON files, user input, settings ou LLM outputs.
- **Data Shape (formato dos dados)**: estrutura esperada de um dado, incluindo fields/keys e seus tipos. `DocumentChunk`, por exemplo, define um data shape com `chunk_id`, `text`, `source_ref` e `metadata`.
- **Runtime Validation (validação em tempo de execução)**: validação feita enquanto o programa roda. Pydantic executa esse tipo de validação e pode levantar exceptions quando os dados não respeitam o modelo.
- **Static Type Checker (checador estático de tipos)**: ferramenta que analisa tipos antes da execução do programa. `mypy` e `pyright` são static type checkers usados para detectar inconsistências de typing sem rodar o código.
- **Boundary Validation (validação nas bordas)**: validação aplicada nos pontos onde dados externos entram no sistema, como APIs, arquivos, configurações e respostas de LLM. Nesses pontos, Pydantic costuma ser mais adequado que `TypedDict`.
- **BaseModel**: classe base do Pydantic usada para definir modelos com validação em runtime. Ao herdar de `BaseModel`, a classe passa a validar, converter e serializar dados conforme os fields definidos.
- **Namespace (espaço de nomes)**: contexto onde nomes ficam disponíveis para import ou uso. `nexusrcm` é o namespace principal do pacote; `nexusrcm.interfaces` é um namespace mais específico.
- **Top-level Public API (API pública de topo)**: conjunto de símbolos expostos diretamente pelo pacote principal. No projeto, `BaseLoader` pode ser importado com `from nexusrcm import BaseLoader` porque foi promovido para essa API.
- **`__all__`**: lista usada por um módulo para declarar quais símbolos fazem parte da sua API pública explícita. Em `src/nexusrcm/__init__.py`, `__all__` inclui apenas os Protocols re-exportados no namespace principal.
